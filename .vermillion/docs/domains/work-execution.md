# 工单执行与恢复

覆盖开工、工单的调度、执行资源声明、依赖、文档变更通知、决策答复、验收提交、主分支合入、后台 worktree 回收，以及运行中断后的恢复。

修改工单状态、执行记录的持久化与查询投影、CLI/RPC 入口、运行事件、角色执行指令、重试与恢复逻辑时应考虑这个领域。涉及工单看板、决策卡或角色界面时同时考虑 UI/UX 领域。单纯修改工单所实现的业务功能、且不改变执行流程时不涉及本领域。

## 开工入口

输入器为空时，「开工」直接登记请求，从当前查看的节点派出准备分支，发送配置的准备提示。所选节点仍在运行时，等待该 turn 结束再派出分支。

输入器有内容时，「发送并开工」直接登记请求，把用户输入与配置的准备提示合成准备分支的第一条消息，保留附件、技能引用及本次模型选择。不会先让设计伙伴运行一轮登记开工。[用户：我点击的时候就直接把开工跟我的输入拼起来发给它了]

已有讨论从当前查看节点派出准备分支，原讨论保留在原位置；New Chat 直接以合成消息开始准备，无需先生成讨论 turn。请求未成功接收时保留输入内容。

准备分支整理文档并建单，结束 turn 后等待调度；调度排到工单时才注入 Worker 指令并开始执行。两种按钮入口使用相同的准备与执行流程。

## 讨论分支与执行归属

会话树的查看位置同时标识会话分支与节点。普通追问从选中的分支发送或 fork；准备与执行分支的活动不改变讨论来源。点击其他分支节点时切换到该节点所属分支。

普通 fork 保留对话上下文和模型配置，不继承开工请求、工单与执行动作的归属。准备或 Worker 分支由调度器明确登记；会话树只对实际登记的执行会话应用 Worker 隐藏及状态规则，普通讨论不随相关工单结束而隐藏。

## Worker 轮次交接与恢复

工单持续归属于 Worker 会话，用户直接进入该会话发起或追加消息时仍沿用该归属。调度器跟踪用户与调度器发起的实际轮次，不因用户交谈重复派工或中断执行。普通进度问答不计为未提交失败；合同调整和决策答复由 Worker 通过对应业务入口落实。

提交被退回后保留成果，等待提交所在 turn 结束并完成调度收尾，再由调度器启动下一轮；用户已启动新轮时跟踪该轮。已有续做安排时不额外发送未提交催办。

后台续接会话保留正在运行的 turn；重新连接与主动中断后重载是不同操作。续做指令在空闲时开启新轮，执行中的工单调整追加到当前轮。引擎明确拒绝追加且确认原轮已结束时，将尚未送达的消息交给下一轮。

轮次事件与执行归属遵循[执行循环规范](../Workbench/Missions/Standards.md)。

## Worker 消息

首次派工提供完整工单执行说明。同一执行会话的后续消息只携带本次增量，不重复身份、工作目录规则、历史记录和通用提交要求。

决策答复包含对应问题、所选选项与用户备注，以及等待答复期间尚需告知的工单调整。引用文档提交通知包含提交 SHA、相关文档 diff 和重新读取最新工单后继续的指令。同一消息内每项答复或调整只出现一次；历史记录保留供查询，不随后续通知重发。
