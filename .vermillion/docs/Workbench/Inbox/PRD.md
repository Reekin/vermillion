# Inbox

Inbox 集中展示所有 workspace 的业务决策、工作受阻通知和已合入通知，每项一张卡片。弹窗只展示待处理消息；全屏界面展示待处理消息与全部已处理记录。消息处理成功后从弹窗移除，已答复决策、已确认通知等已处理消息仅在全屏 Inbox 中保留查看，重新打开应用后仍可查看。

已合入通知主区展示工单标题、证据摘要和逐条验收结果，每条用验收时的实测描述而不是验收条目原文；commit、命令输出、review 意见处置、验收过程和 diff 概况放在可折叠的技术详情里。待处理通知的底部操作为知道了、附理由回滚；知道了将通知标记为已处理。Inbox 未处理计数不包含已处理记录。

某一项的数据损坏或加载失败时，Inbox 显示失败原因，不显示为空。Explorer 同样。

## 决策卡

决策卡要让用户看懂当前问题以及不同选择的结果。主界面不应直接铺开执行日志、源码路径和验收报告。

打开 Inbox 后，每张卡先显示所属工单，用简短文字说明发生了什么、为什么需要用户决定，再展示选项及各自影响。推荐项必须解释推荐理由；选项说明直接可见，不能只放在悬停提示里。

源码定位、测试结果与证据路径放在可展开的“技术详情”中；技术详情只放核对这个决定所需的信息，工作过程（跑过哪些命令、review 采纳记录、资源清理）属于工单证据，不进决策卡。需要深入了解时可以打开对应工单或执行会话；默认视图只保留做决定需要的信息。答复结果及相关工单状态在全屏 Inbox 的已处理记录中显示。

准备和 Worker 的业务决策支持自由答复：只填文字、不选预设选项也可提交。Inbox 和执行会话的“回复此决策”模式共用答复入口，选择的卡片、答复与消息关联保存；成功后卡片进入已处理记录，消息只交付一次给该工作的当前执行分支。

进入有一张待决策的执行会话，composer 默认显示该问题及“回复此决策”模式；多张待决策时明确选择一张，不自动答复其余卡片。发送答复解除所选决策等待，恢复发起决策时的推进方式；自动推进仍受 workspace 开关、暂停、其他决策、依赖和资源约束，答复不隐式解除用户后来设置的暂停。没有其他阻塞时继续当前工作，不另发重复唤醒。发起决策时处于人工接管的工作仍由人工推进。

用户可切为“普通消息”询问方案或进度。普通消息只交谈，不登记答复、不解除业务等待、不按文本推断用户选择，也不覆盖决策前的推进方式；允许在等待决策期间进行此类沟通，但不据此派发业务执行或放行提交。答复仍不足以推进时，由执行者提出需要澄清的问题并维持明确的业务等待，不擅自推断授权。

已答复而尚未送达的结果显示“答复已登记，等待送达”及具体原因；传输故障不撤销已答复记录，不产生第二份答复。重复提交不重复送达，取消或迁移后按当前有效归属处理。

合入故障的重试进度、立即重试、附说明转交 Agent 和取消遵循[合入进度与处置](../Missions/PRD.md#合入进度与处置)，与工单详情使用相同状态和操作。需要用户判断的合入阻塞及时进入 Inbox；自定义说明随转交实际送达处理该单的 Agent。

运行故障以工作受阻通知呈现，显示原因、关联工作和重试、暂停、取消等适用操作，不要求填写业务决策答复。故障分类与重试规则见[运行失败与恢复](../Missions/PRD.md#运行失败与恢复)。人工接管或重试使旧故障安排失效时，同步处理原受阻通知，不留下阻止执行的未答复决策。未处理及已处理记录的展示沿用 Inbox 规则。

决策卡用于必须由用户选择的业务取舍、权限授权、需要用户判断的合入阻塞。技术问题、验证条件不足或尚未完成由执行者继续处理，不因审阅或验证达到固定轮数而要求用户放宽要求。卡片说明已经尝试的处置、剩余问题与每个选择的实际影响。

决策卡的字段：一句话问题、两三句上下文、每个选项的动作与后果、推荐项及理由、可折叠的技术详情、发起它的会话。GUI 与 CLI 读取相同内容。卡片上有「进入会话」可直接打开发起它的会话进一步沟通（统一进入工作台 → 会话并定位当前执行分支），结论回写关联工作。

前置工单被取消时，工作台也可发起需要用户选择如何处置依赖的业务决策，见 [工作与工单](../Missions/PRD.md)。
