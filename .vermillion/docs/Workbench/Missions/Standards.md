# 执行循环规范

执行模型围绕工单、当前动作和等待条件组织。合同、依赖、主工作区修复与运行异常共用交接和恢复机制；问题类型决定处理者与恢复条件，不各自增加独立调度循环。[用户：我不希望出现复杂脆弱的循环。]

`needs` 只声明共享且不能同时操作的具体对象，同一对象使用同一资源名。独立实例不声明资源，工具类别 `browser`、`desktop` 不作为互斥资源名；前置工单只用 `dependsOn` 表达。资源声明不提供跨 workspace 互斥保证。

调度、CLI/RPC、持久化和角色指令使用同一套工作阶段、阻塞和恢复规则。持久化记录是进度依据，事件驱动派发与核对；需要延迟恢复时使用明确的重试时间，不以界面轮询推动执行。

任何等待都有可查询的原因、处理者和恢复条件。交接记录区分待接手、处理中、待决策与已解决；送达回执、agent 文本和 turn 结束不能代替处置结果。恢复以实际合同、依赖、运行时或 Git 状态为依据，不以修改标签或重复发送消息为依据。

正常执行、启动失败、运行异常和重启恢复共用同一流程；不另建可绕过验收、权限和依赖的自救通道。重试续接未完成动作，保留原会话与成果，不重复已完成的外部操作。

语义判断由当前责任 agent 完成，程序负责确定性状态转换与动作约束。运行日志描述实际阶段和原因，不能仅凭会话 ID 变化推断合同变更。

自动技术处置限于既有需求与授权。合同调整归管家，工单代码修改归 Worker，主工作区恢复归 WorkspaceRepair，主分支合入与回滚由工作台串行执行。角色通过持久化动作交接，不以自由对话替代工单和阻塞记录。

用户可见内容说明工作结果、等待原因和实际选择；参数、会话 ID、命令输出等诊断信息放详情与 CLI。规范所约束的具体行为见 [PRD](PRD.md)。
