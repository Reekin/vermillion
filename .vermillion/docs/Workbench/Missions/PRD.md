# 任务与工单

## 任务

Mission 是一项工作目标及其文档 revision 序列，状态为进行中、已完成、已取消。revision 是「这些文档在这个 commit 的内容」：从提交弹窗以「新任务」创建，或以「补充到现有任务」追加；勾选的文档里有本地改动的先提交，没有改动的直接引用当前 commit，所以已提交的文档也能开任务。「仅提交」只保存文档，不产生任务也不触发处理。

任务由管家判断目标是否达成并收尾：目标已达成标为已完成，目标放弃标为已取消。系统在完成任务时检查本任务下没有未结束的工单；工单全部结束本身不代表目标达成。之后补充 revision 会让任务回到进行中。

重复工单被取消、需求由其他任务的工单承接时，管家在原任务登记承接工单。承接工作尚未完成时原任务保持进行中；本任务工单全部结束及承接工单状态变化时，系统唤醒管家判断是否可以收尾。已处于这一状态的进行中任务也应得到收尾处理。管家确认承接工单已完成需求后，将原任务标为已完成，保存面向用户的结果说明和关联工单。任务卡片展示结果说明，关联工单可点击查看详情。

任务看板在 Workspaces → 任务，布局参考 [mock/workspaces.html](mock/workspaces.html)（截图 [mock/workspaces.png](mock/workspaces.png)，上半弹窗、下半页面），工作状态按下述流转显示。顶部一行工具条：调度开关、并发上限步进器、一句等宽统计（执行中 / 等待中 / 已结束的数量），没有说明文字。

每个任务一张卡片。头部：状态标签、标题、右侧相对时间（页面模式下再加 revision 数与短 commit）、「管家会话」按钮、一个「···」菜单；「取消任务」只在这个菜单里，不直接摆在卡片上。正文：摘要（最多两行）、管家最近一句说明（一行）。下面每张工单一行：风险标签、标题、运行信息（等宽小字：角色、turn 数、最近时间；页面模式写全，弹窗模式只留 turn 数与时间）、状态胶囊、然后是固定的两个位：取消 × 和「会话」。× 只在这一行 hover 时显示，但始终占位，所以「会话」与状态列在所有行里对齐；没有会话的工单（排队中）会话位留空。运行记录不再单独成行，会话入口只出现一次。

独立工单不放在卡片里，用一个 eyebrow 小标题「独立工单」加一个带边框的列表直接列工单行。

以弹窗快速查看时只列进行中的任务和未关闭的独立工单，工具条右端一个链接「另有 N 项已结束」，点击即展开为页面；展开为页面后显示全部，已完成任务的工单标题和状态降灰。取消任务会先取消它下面所有未结束的工单。

任务看板和 Inbox 里的「会话」都跳到 Workspaces → 会话 并选中那个会话。

## 工单

WorkItem 是可独立执行和验收的单位，来自管家拆单，或由设计伙伴直接创建（独立工单，无 Mission：打包、测试等操作，以及不改设计的 bug 修复）。有允许路径的工单在独立分支和 worktree 里执行；没有的（纯操作）在 workspace 根执行。

工单主体是对文档的引用（路径、段落、commit），不另存需求副本。自身保存标题、范围与允许路径、验收条目、所需资源、依赖的工单、运行记录、证据、review 处置和决策。验收条目只描述做完后能观察到什么，不规定验收方法；每条一到两个短句，先说从哪进、再说看到什么。证据摘要面向用户，只说改动后能看到的行为变化；commit、分支、测试命令、review 和验收过程记在证据的命令与附件里，不写进摘要。[用户：这个验收单也是叽里呱啦看不懂]

风险等级：R0 只读、R1 可丢弃制品、R2 项目内可回滚。影响共享环境的操作（发布、部署、推送远端等）不建工单，由用户在思考页用现做模式和设计伙伴一起完成。

### 工单面板

工单有一个统一的详情面板，以弹窗打开：标题、状态胶囊、风险标签、目标、范围与允许路径、验收条目、引用的文档、依赖的工单、运行记录、证据、决策；底部一个「会话」按钮跳到 Workspaces → 会话并选中它的会话（排队中的没有会话则不显示）。任务看板里点击工单行的标题打开这个面板。

会话消息里出现的工单 id（管家、Worker、Supervisor 会话的合同和通知，设计伙伴建单后的回复，决策卡里的相关工单）不以裸 id 显示，渲染成一枚工单标记：风险标签、标题、状态胶囊，状态随工单实时变化。点击标记打开工单面板。[用户：类似于游戏里点击聊天栏里的道具]

## 流转

### 正常执行

工单从排队进入执行，Worker 在原 worktree 完成开发、review 和真实验收，提交前 rebase 到当前主分支。工作台接收证据并执行合入；合入成功后关闭工单、清理 worktree，Inbox 收到已合入通知。纯操作工单通过验收后直接关闭。用户在已合入通知上可以附理由回滚：工作台还原这次合并，原 Worker 带着理由续做。

调度器按 workspace 并发上限和资源需求取单，默认并发 2；同一 workspace 内共享且不能同时操作的具体对象不能同时分配给多张工单，依赖全部关闭且没有未解决阻塞才执行。独立浏览器、桌面和验收实例可以并行，不因使用同类工具而互斥。工单的工作进度与等待原因分开表达：能取起的排队、正在执行、等待合入、已关闭、已取消；受阻时另有明确的等待原因，需要用户取舍时展示待决策。等待不占 Worker 并发或执行资源，保留成果、原会话与 worktree。

`workItem.update` 支持调整 `needs`，调整后调度器按当前声明取单；现有使用独立验收实例的未结束工单移除泛化的 `browser`、`desktop` 声明，保留其他合同内容与成果。

### 阻塞与交接

每个阻塞保存原因、相关证据、处理者、处置进度和恢复所需的具体动作。处理者是原 Worker、负责本单的管家、workspace 修复 agent 或工作台；用户只承担必须由用户决定的业务取舍、权限授权，以及自动恢复用尽后的选择。任务看板在受阻工单行显示简短原因与当前处理者；详情能查看处理会话、最近处置、等待条件和下一次重试时间。

| 问题 | 处理者与恢复方式 |
| --- | --- |
| 本单实现或验收未通过 | 原 Worker 按具体失败项修复并重新提交；发现合同矛盾时转交管家。 |
| 目标、允许范围或验收与现实冲突 | 管家读取原合同、证据和已有决定，更新原单合同、调整依赖或取消；实际处置落地后恢复。 |
| 等待另一张工单 | 工作台等前置关闭后恢复；前置取消或需要调整依赖时交本单管家。 |
| 本单分支与主分支代码冲突 | 原 Worker 在自己的 worktree rebase、解决冲突并更新受影响的验证，再提交。 |
| 主工作区状态阻挡合入 | workspace 修复 agent 处理主工作区，工作台重新检查后重试合入。 |
| 启动、消息送达或运行时失败 | 工作台保留失败阶段，按重试规则恢复该阶段的处理者。 |
| 必须由用户做的取舍 | 决策卡保存问题，答复交负责处置的 agent 落实，再检查恢复条件。 |

上报成功表示问题已持久化并有明确处理者。消息送达、会话结束和问题解决分别记录；管家只回复文字、处理者失败退出，都不会被当成完成。处理者结束一轮仍未更新合同、登记依赖、完成修复或发起必要决策时，工作台在原会话要求落实具体动作；连续未落实交由下述恢复规则处理。阻塞期间不反复唤醒等待中的 Worker。

同一问题在事实、合同和成果没有变化时，不重复提交相同失败证据或反复重试同一动作；原 Worker 应上报原因交管家处理。重复上报归入当前未解决问题，保留补充信息。程序按状态和明确动作调度，语义判断由已有责任 agent 完成，不额外增加分类或通用救援 agent。

### 合同与依赖

Worker 用 `workItem.escalate` 上报合同问题，用 `workItem.defer` 登记前置工单，随后结束本轮。管家通过工单更新、取消或决策卡处置，不与 Worker 自由对话。[用户：让一个任务上下游的 agent 相互 steer 不合适，只补 Worker→管家这一条，落文件、不自由回复] 合同等待、依赖等待与待决策均不计运行失败。前置可以属于其他任务；创建、调整和登记依赖都检查目标存在且不形成循环，拒绝时说明依赖链并交管家重新安排。

独立工单正常执行时不启动管家。首次合同问题、需要落实的合同决定或前置取消需要处置时，按该工单启动管家；后续复用该会话。管家处理原单，只有确实需要改变拆分时才调整工单关系；独立工单保持无 Mission。取消前置后，其有任务和无任务的依赖方均有管家接手。

管家在已确定的需求和授权内自行调整范围、依赖和实现安排。范围外的测试失败先核对归因：已有决定允许例外时把例外准确写入原单验收；没有例外依据时安排必要修复与依赖，不把放宽验收当作技术自救。需求含义不明确时先读引用文档和来源设计会话；只有资料无法回答且需要用户取舍时才发决策卡。

用户对 Worker 工作的答复先交原 Worker 理解；普通答复继续执行，涉及目标、范围或验收变化时先上报管家，合同更新前暂停开发与提交。已由管家处理的合同问题，其决策答复直接回该管家落实；主工作区问题的答复回修复 agent。沿用当前责任会话理解选项和备注，不新增 Inbox 分类选择；仅保存答复文字不解除合同阻塞。技术问题或已有明确决定不重复询问用户。

进行中调整合同时，Worker 立即收到并重新读取；调整送达那一轮里的提交视为旧合同作废，下一轮按新合同续做。待决策期间的调整同时写入决策卡上下文，答复与最终合同一起交给处理者。只有落实了当前问题所需的合同内容或明确处置，才能解除该阻塞，改标题、补引用或只写说明不视为解决。审阅者不能自行新增验收要求。

### 合入与主工作区修复

工作台统一串行执行主工作区的合入、回滚和修复；Worker 仅在自己的 worktree 解决本单代码冲突。验收通过的证据及待合入提交保留，主工作区环境故障不变成开发返工。

合入、回滚或其清理阶段出现主工作区故障时，按 workspace 唤醒独立的 **WorkspaceRepair（工作区修复）** agent，cwd 为 workspace 根，同一 workspace 同时只有一个修复会话执行；后续修复复用该会话。[用户：那给主工作区安排个单独的agent，只在遇到这类问题时被唤醒？] 它收到具体失败阶段、错误和受影响工单，检查并恢复主工作区，使工作台能够继续合入。同一主工作区故障关联所有受影响工单，不为每张单各开一个修复 agent。修复期间暂停该 workspace 的自动合入与回滚，其他 worktree 的开发继续。

修复 agent 可以自动处理已确认属于工作台的残留 Git 操作和可恢复的本地环境故障，记录原因与处置结果；保留他人未提交改动和已有成果，不擅自覆盖、删除、提交或藏入 stash。归属不明且无法在保留现状的前提下恢复时，才发决策卡说明需要选择什么；它不修改产品功能、不代替 Worker 解决业务代码冲突、不承担发布部署。

修复完成后由工作台重新检查主工作区并重试待合入成果；若分支此时需要处理代码冲突，交原 Worker 在 worktree 处理，只更新受影响的验证。已经完成的合入不因后续清理失败再次执行，清理问题由修复 agent 继续处理。

### 中断与恢复

从创建 worktree、打开会话、发送消息到执行与合入，各阶段失败都进入可查询的运行记录和恢复流程，不仅打印日志。工作台启动时以及处理者异常结束后核对持久化进度与运行时状态，从未完成的动作继续；进程仍在运行工具或等待模型输出时，不仅因耗时长判为失败。

运行异常恢复原处理者会话，失败原因作为下一条消息送达；仅在原会话确实无法恢复时新建，并附完整合同、当前阻塞、已有决定、成果位置与未完成动作。Worker、管家和修复 agent 的运行失败按各自当前处理过程计数，不把管家或修复 agent 的失败算给等待中的 Worker。连续多轮没有落实动作时先明确缺少的动作，仍无进展则记一次失败并延迟恢复，不通过不断换 agent 丢弃上下文。

每个失败过程最多自动重试 4 次，间隔 1、5、30、300 分钟；第 5 次失败后保持阻塞，发决策卡展示最近原因、已尝试的恢复和影响，允许再试或取消当前工作。重试从原处理过程继续并清零本轮失败计数，取消按关联工作实际范围说明后果；同一故障不为每张受影响工单重复发卡。[用户：允许重试4次，分别间隔1/5/30/300分钟][用户：只要是fail，都算外部原因吧？可以计attempts，也可以够次数后变决策卡，但没必要换worker]

### CLI 诊断与自救

所有处置都有 CLI/RPC 入口，与自动调度共用状态判断。命令返回实际结果、当前等待原因和合法下一步，不把写入成功描述为执行完成。桌面调度器不在线时，CLI 明确说明记录已保存、尚未派发；运行端提供构建标识，便于区分源码更新与正在运行的版本。

- `workItem.diagnose`：汇总当前工作阶段、所有阻塞、处理者及会话、依赖、调度开关、资源占用、最近失败、下次重试和可用动作。无阻塞的排队也说明在等并发、资源还是调度器启动。
- `workItem.escalate`：保留合同上报，并支持报告执行环境阻塞，记录证据和建议；主工作区故障交修复 agent，其他超出原 Worker 能力或范围的问题交管家落实处置。
- `workItem.recover`：重新核对运行状态与恢复条件，补送未送达的交接、恢复失联处理者，或在故障已排除后立即重试该失败阶段。报告实际采取的动作；仍有依赖、合同或决策阻塞时保持等待并说明处理者，不绕过条件。活动处理者不重复启动，已完成阶段不重复执行。
- `workspace.repair.submit`：修复 agent 提交关联故障的处置结果与证据，由工作台检查实际恢复条件并续接失败阶段；检查仍不通过时保留问题交原修复会话继续，不能凭一句“已修复”清除阻塞。
- `decision.withdraw`：发起者撤回尚未答复且已澄清或过时的决策，说明原因；只解除此卡的等待，回到当前问题的责任 agent 继续处置，其他阻塞照常保留，不伪造用户答复。
- CLI 帮助可查询单个方法的参数、适用状态和示例；参数或状态错误返回明确原因及下一步动作。

自救不提供任意改状态、强制通过验收、伪造用户授权或丢弃成果的入口。人工无需在多个会话之间转述技术问题、重抄决定或靠反复重启推进；需要人介入时，卡片给出系统已经处理到哪里和剩下的具体选择。
