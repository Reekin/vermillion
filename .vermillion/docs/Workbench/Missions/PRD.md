# 工作与工单

WorkItem 是可独立执行和验收的单位，由开工分支创建（见 [工作台 · 开工](../Think/PRD.md)），或由用户在 工作台 → 工作 页手动创建（引用手改的文档或 Issue，冷启动一个 Worker）。允许路径限定代码修改范围；是否使用 worktree 由 Worker 根据项目和本次工作判断，需要时自行创建并登记目录与分支，否则在 workspace 根执行。

工单主体是对文档的引用（路径、段落、commit），不另存需求副本。自身保存标题、范围与允许路径、验收条目、所需资源、依赖的工单、来源设计会话与执行会话、运行记录、证据、review 处置和决策。验收条目只描述做完后能观察到什么，不规定验收方法；每条一到两个短句，先说从哪进、再说看到什么。证据摘要面向用户，只说改动后能看到的行为变化；commit、分支、测试命令、review 和验收过程记在证据的命令与附件里，不写进摘要。

风险等级：R0 只读、R1 可丢弃制品、R2 项目内可回滚。影响共享环境的操作（发布、部署、推送远端等）不建工单，由用户在工作台会话页和设计伙伴一起完成。

## 引用定位

工单引用由文件路径、固定 commit、可选段落定位与独立的说明组成。段落定位使用文档实际标题；同名标题用完整祖先标题路径区分。定位不包含自由描述或行号，说明不参与变化判断；省略段落定位表示引用全文。

创建工单或更新 refs 时，工作台在指定 commit 上校验文件与段落可以唯一定位，无法定位时指出具体引用并拒绝该次写入。已保存引用无法定位时明确报告，不静默按全文处理。标题被删除或更名属于原引用范围的变化，须报告定位失效并由合同更新确认新位置，不自动猜测替代标题。

文档合入按每条引用的实际范围判断：范围外变化不升级合同、不发送文档变更通知、不更新该条引用 commit；范围内变化只更新对应引用并发送相关差异。同文件中未变化的其他引用保留原 commit。通知与合同更新遵循[执行循环规范](Standards.md#执行消息)。

## 工作

工作覆盖一次开工从准备到交付的全过程。work.start 接收成功即产生可查询、可管理的工作，名称取开工范围或来源会话标题，准备期间可完善。准备请求承载这份工作，不提前创建空工单。一份工作包含一次准备及其产生的多张独立工单；准备完成后仍保留工作入口、来源、准备结果和关联工单。手动创建及领域自动创建的独立工单直接管理，不补造准备阶段。

业务阶段、推进方式、当前执行会话与活动轮次、等待原因分别表达。推进方式为自动、人工接管或暂停；准备、排队、执行和合入属于业务阶段。界面按当前事实显示准备中、执行中、已中断、等待决策、人工接管、已暂停及结束结果。没有活动执行时不显示进行中；等待不占执行并发，停止中的执行在确认退出前仍保留占用。

准备完成结果明确关联本次全部工单及其文档依据和所需目录登记，工作台核对交接结果后等待准备轮退出，再开放工单执行。单纯轮次正常结束或已经出现一张工单不代表准备完成。准备被暂停、取消或由人工接管时，不因已有部分工单而提前派发。准备完成后的各张工单独立推进，按各自依赖取单。

工作详情展示准备及工单的当前情况；全部工单结束后显示完成或含取消的结束结果，不把部分取消显示为全部交付。工作层提供暂停全部、恢复全部自动推进和取消剩余工作，只作用于未结束部分；单张工单操作只作用于本单，已完成成果与记录保留。准备中的操作目标为准备过程，进入工单执行分支后的目标为该工单。

## 看板

领域 Owner 可依照[自动修复授权](../Domains/PRD.md#自动修复授权)为 Issue 创建修复工单。工单关联来源 Issue、巡检会话和授权判断，进入相同的 Worker 调度、独立审阅及验收流程。

工作看板在 工作台 → 工作，展示当前 workspace 的全部工作及独立工单。顶部工具条提供自动推进开关、执行并发上限与执行中、等待中、已结束统计；统计按准备过程和独立执行工单计数，工作分组不重复计数。

每次开工作为一个可展开的工作条目，显示名称和来源会话；同一来源多次开工分别管理。建单前显示准备状态和操作，建单后在原条目下展示关联工单。无准备过程的工单归在「独立工单」组。卡片、间距和信息分组参考[交互示意页](mock/workspaces.html)，包含[收起](mock/workspaces.png)、[展开](mock/expanded.png)、[悬停](mock/hover.png)和[窄窗口](mock/narrow.png)效果；业务内容与操作遵循本文。

每张工单一行：风险标签、标题、运行信息（等宽小字：turn 数、最近时间）、状态、适用的暂停或恢复入口，以及固定的取消 × 和「会话」位。× 只在这一行 hover 时显示，但始终占位，所以「会话」与状态列在所有行里对齐；没有会话的工单会话位留空。工单处于等待时，状态使用具体阶段，例如「退回待续做」「等待重试」「等待用户」，并在次行显示简短等待原因，不用笼统的「排队中」隐藏已经发生的退回、失败或恢复条件。「会话」跳到该工单的执行会话：统一进入工作台 → 会话，fork 分支定位到对应节点，冷启动会话直接选中。

看板中已结束的标题和状态降灰。工作条目依次按包含活动准备或执行、包含其他未结束部分、全部已结束排列；组内工单也按执行中、其他未结束、已结束排列。已结束指已关闭或已取消，等待用户属于未结束；同一优先级保留原有顺序，状态变化后按当前状态更新排序。标题栏的 workspace 选择器切换看板范围。

## 工单面板

工单有一个统一的详情面板，以弹窗打开。弹窗标题使用工单标题，首屏固定回答当前在做什么、为什么等待、下一步由谁处理、用户是否需要操作；风险、状态、工单 id 和时间作为辅助信息。「会话」进入执行会话，「来源」回到来源设计会话的 fork 点，滚动长内容时仍能直接使用。

当前进展按工单、执行动作、合入动作和运行记录的真实状态生成。等待时显示具体阶段、最近原因、当前处理者、恢复条件或下一步，以及已等待时长或下一次重试时间；无需用户操作时明确说明。提交被退回后，依次区分「提交已退回」「等待提交所在 turn 结束」「等待调度续接」「Worker 已收到退回并处理」，不把这些阶段统一显示成「排队中」。失败信息使用可读摘要，展开后提供原始原因和阻塞文件；没有记录到的细节不推断。

当前进展下方是按时间排列的关键事件，默认显示最近事件，可展开完整历史。事件使用用户可理解的动作描述，覆盖开始执行、合同调整、提交验收、合入检查、退回及通知送达、恢复执行、合入完成；run id、内部 stage 和 `done` 等内部字段只出现在技术详情里。

其余材料按「任务要求」「验收结果」「审阅意见」「检查与附件」分组折叠。折叠标题给出目标、通过数、处置数等摘要；验收要求与对应结果成对展示，不在面板不同位置重复全文。空的依赖、决策、附件等区块不占据页面；待用户答复的决策提升到当前进展区并提供操作。工单关闭后，当前进展改为成果摘要、合入 commit 和验收结论，历史退回与失败保留在事件记录中。

会话消息里出现的工单 id（开工分支的合同、设计伙伴的回复、决策卡里的相关工单）不以裸 id 显示，渲染成一枚工单标记：风险标签、标题、状态胶囊，状态随工单实时变化。点击标记进入工作台 → 工作并定位工单详情。

## 流转

工作先准备，准备交接后工单依次排队、执行、等待合入、关闭；取消为另一结束结果。暂停、人工接管、等待条件与业务阶段分别保留，保留成果、执行会话与 worktree。

自动推进默认开启，执行并发上限默认为 2；已有 workspace 沿用保存的开关和并发设置。准备和 Worker 使用同一执行并发限制，人工续跑也登记实际占用。调度按 workspace 并发上限和资源需求取单，`dependsOn` 全部关闭且 `needs` 声明的资源没有被执行中的工单占用才取。同一 workspace 内共享且不能同时操作的具体对象不能同时分配给多张工单；独立浏览器、桌面和验收实例可以并行，不因使用同类工具而互斥。`workItem.update` 支持调整 `needs`，调整后调度器按当前声明取单。前置工单被取消时，依赖它的工单转为等待用户并说明原因。

调度器排到工单时，先在执行会话追加 Worker 开发者指令并应用 Worker 模型配置，再把合同作为下一条消息送过去续跑；普通恢复不重复追加相同指令。没有来源会话的独立工单冷启动 Worker，合同作为首条消息。会话 cwd 始终保持 workspace 根目录；使用 worktree 时，Worker 在工具调用中显式指定对应工作目录或文件绝对路径。

Worker 在选定的工作目录完成开发、review 和冷验证。使用 worktree 时，提交前 rebase 到当前主分支；在 workspace 根执行时直接提交本次成果。工作台接收证据，默认自动合入，也可按下述方式转交 Agent 处理；合入成功后立即关闭工单，Inbox 收到已合入通知，不等待重试计时或 worktree 清理。纯操作工单及仅交付仓库外独立产物的工单通过验证后直接关闭，保留证据与产物位置，无需 Git 提交或合入。允许路径中的仓库外路径不参与 Git 成果检查；同时包含仓库内成果时，仓库内部分仍须完成提交检查与合入。用户在已合入通知上可以附理由回滚：工作台还原这次合并，原 Worker 带着理由续做。

worktree 清理由后台低频维护执行，默认每 5 分钟检查一次工作台登记的候选目录，不在工单刚结束时立即尝试删除。 Worker 的活动 turn 结束后先发出退订请求，不等待引擎立即卸载。维护只清理已不再使用且归属匹配的 worktree；排队、执行、待决策或续做仍需使用的目录均保留。目录被占用或清理失败时留待下一次检查，不重开工单、不占用 Worker 并发，也不产生清理决策卡。候选记录可跨进程重启保留，同一维护操作提供 CLI 入口。

需要改变尚未获准的需求、超出授权或存在必须由用户选择的取舍时，Worker 发决策卡并结束本轮，工单转为等待用户；用户在决策卡或对应会话的决策回复模式中答复，交接规则见 [Inbox · 决策卡](../Inbox/PRD.md#决策卡)。能自行处理的技术问题继续处理，不因 review 或验证达到固定轮数而自动要求用户决定。分支与主分支代码冲突由 Worker 自己在 worktree rebase 解决后重交。

合同修订号只跟随交付物相关字段：objective、scope、acceptance 和 refs。调整 title、needs、dependsOn 不改变修订号，执行中的提交不因这些调整被拒。提交明确对应所依据的合同，工作台只接受符合当前合同的提交。读取最新合同并处理变更影响后可在当前轮提交；依据过期时保留成果与已有证据，要求更新依据及受影响的结果，不以轮次切换作为提交条件。

执行期间来自其他会话或用户的合同调整与引用文档合入，工作台立即送进执行会话。执行会话自己发起的合同调整与文档合入只落记录，不回送、不中断当前轮：Worker 通过 `workItem.update` 加入 dependsOn 后可以正常收尾本轮，工作台等该轮结束再按等待条件处理。每条送达通知带类型（合同调整、文档合入、提交退回、恢复执行、催办），按顺序累积到送达时一起交付，送达后消费；引用文档 diff 只出现在通知和执行历史里，不写入合同本体。`workItem.cancel` 中断执行会话，将已登记的 worktree 纳入后台清理候选，按上述维护规则回收。

### 合入进度与处置

工单区分「等待合入」「正在合入」「合入失败，等待重试」和「Agent 处理合入」。列表在原状态位置呈现简短进度，详情展示最近失败原因、阻塞文件、已失败次数和下次重试时间。首次尝试不算重试；自动重试标明「第 N/4 次」，等待期间说明下一次的序号和时间。

合入失败后，工单详情提供「立即重试」「交给 Agent 合入」和取消入口，无需等自动重试用尽。立即重试执行当前未完成的合入动作并更新进度。Inbox 的合入故障项使用同一处置流程，转交 Agent 时允许附自定义说明。

转交后取消本单的自动合入重试安排，恢复原 Worker 会话，送达当前成果、失败原因、合入进度和用户说明；不重做已通过且未受影响的开发与验收。Agent 可以处理本单冲突、rebase 和最终合入。自动合入与 Agent 接管同一时刻只有一个执行者；正在执行的主分支操作结束后才移交，其他工单的主分支操作也不能与其并发。暂停、取消和恢复沿用工单现有规则，应用重启保留接管归属，不自动切回调度器合入。

Agent 完成后通过 CLI/RPC 交回合入结果，工作台核对成果确已进入主分支，立即关闭工单并发出通知。Git 已完成但工单尚未收尾时，继续核对和登记结果，不重复合并或等待原退避时间。

需要用户判断的主工作区改动归属等阻塞，在工单和 Inbox 中明确说明原因与待选择事项，不等数小时退避结束才告知。可由本单处理的技术问题交回 Worker；可能自行恢复的临时故障继续有限重试。不同阶段的等待均有明确处理者和可执行的下一步。

### 执行、审阅与验证

执行与材料交接由 [Worker](../../../../packages/workbench/roles/worker.md)、[Reviewer](../../../../packages/workbench/roles/reviewer.md) 和 [Verifier](../../../../packages/workbench/roles/verifier.md) 指令规定。界面验收实例由工作台在独立桌面启动，不出现在用户操作屏幕上。

验证结果区分通过、发现缺陷、条件不足和未完成；条件不足与未完成不算产品缺陷，也不算通过。只有要求全部得到验证且符合文档终态时才能完成交付。有效的逐项观察和证据随续做保留，无关文档更新不使其失效；修复或需求变化只复核受影响部分。审阅与验证的交接、进度查询和续做由角色 prompt 规定。

### 执行控制

自动推进开关作用于当前 workspace 的准备、Worker 自动启动、自动续轮与重试，以及后台自动巡检启动。关闭后不启动新的自动动作，活动轮次、已经开始的合入操作和结果结算继续；显式用户操作仍可进行，依赖与共享资源约束仍生效。恢复开关不解除某项工作的暂停、人工接管或业务决策等待。

准备和 Worker 均可在准备中、排队、等待重试、运行中暂停。暂停撤销待执行安排，中止当前活动轮，保留已有成果，不计作失败。Stop 对已绑定工作的正式轮次执行同一暂停；普通讨论与尚未绑定工作的发送操作仍按会话自身规则停止。取消明确结束目标工作，保留历史，不再调度。暂停、取消和人工接管跨应用重启保持。

原执行分支的活动轮次中追加消息，只补充当前轮，不创建第二次执行、不重置失败计数、不改变推进方式。分支空闲时人工发送新消息，进入人工接管，撤销旧的自动续跑与故障恢复安排；不按消息文字猜测是进度问答还是续做。发送前登记当前执行并检查资源、依赖；被阻塞时消息保留待发送并说明原因，不让 agent 绕过业务约束执行。等待业务决策时的普通交谈与正式答复遵循 Inbox 的专门规则。

人工接管的活动轮结束后，有准备完成、提交或决策等明确交接结果则正常处理；没有交接结果则显示等待手动继续，释放活动执行占用，不自动催办。用户可继续发消息，或明确恢复自动推进。人工接管中确认的提交仍进入正常验收与合入。恢复自动推进与立即重试均不重复发送已受理的消息，不越过尚未解决的依赖、资源和决策等待。

在执行分支的历史节点提供“从此处继续执行”：先停止原执行并确认退出，再以所选节点创建分支并转移当前准备或工单的执行归属；已有工单、文档、工作目录、证据和待决策关系保持，启动方式为人工接管。新分支收到所选历史点之后仍有效的工作进度、合同、成果位置和待处理事项摘要，不复制无效续跑提示。迁移不回滚磁盘成果。旧分支保留历史及前往当前执行的入口，不能再自动推进或提交这份工作；迁移失败保留可查询的暂停状态及当前有效归属，不启动两个执行者。普通 fork 只创建讨论分支，不迁移工作。

工作控制、会话发送与当前工作状态条使用同一执行归属。定时重试到点只重新检查当前条件；人工消息、暂停、取消、迁移或新的执行已经使旧安排失效时，不再发送旧续跑提示。

### 运行失败与恢复

从创建 worktree、打开会话、发送消息到执行与合入，各阶段失败都进入可查询记录，包含最近原因、已尝试的处置和下一步。活动工具或等待模型输出不因耗时长被判为失败。错误信息保留原始详情，面向用户展示可读摘要。

额度不足、网络错误等是中断原因，统一呈现“已中断”，原因与下一次尝试时间在详情中展示，不为故障原因增加独立状态。是否自动重试与显示状态分别处理。明确的额度耗尽、认证失效、配置错误停止自动尝试；有可信恢复时间时展示该时间，等待用户处理后重试。临时网络错误、暂时限流及原因不明的通用 429 使用有限重试，不将通用 429 推断为额度耗尽。临时故障最多自动重试四次，默认间隔 1、5、30、300 分钟；服务端有明确重试时间时采用该时间。用尽后进入工作受阻，提供重试、暂停、取消，不创建业务决策卡。合入故障的提前处置沿用合入进度与处置。

重试次数属于当前故障恢复过程，历史永久保留；确认执行已成功恢复并完成一个正常业务轮次后结束该恢复过程。人工接管、迁移或显式重试使旧恢复安排失效，后续失败独立记录。用户暂停、取消与普通问答不计作失败。

消息是否已被引擎受理不明确时先核对实际消息与轮次；无法确认时显示等待确认并提供重查，不以新消息重复尝试。准备和 Worker 首次派发提供完整任务说明，后续仅发送有效进度与必要增量。恢复提示不改变原任务目标，不重放过时的催办和已消费通知。

自动执行轮正常结束但未登记交接结果时，最多进行一次收尾提醒；仍无结果则显示“缺少交接结果”并等待处理，不将其计作网络故障开启另一轮退避催办。人工轮没有交接结果按人工接管规则等待。

工作台重启后核对持久化执行与引擎状态：活动轮继续跟踪，已结束的轮补做结算，发送结果不明时先确认；暂停与人工接管保持不变。旧轮结束、旧发送回执和旧重试只补充自身历史，不改变新的执行、恢复暂停或覆盖取消。单纯缺少内存跟踪记录不触发续跑。

### CLI

Worker 可通过 `asksource` 询问开单来源；会话消息读取和通用 `steer` 的行为见[会话读取与通信](../Roles/PRD.md#会话)。来源位置使用工单记录的设计会话与开单 turn。

工作查询、准备完成登记、单项及整份工作暂停/恢复/取消、人工发送、从指定节点继续执行、状态诊断和决策回复均有 CLI/RPC 入口，与界面和自动调度共用状态判断。现有业务入口包括：`work.start`、`workItem.create / update / submit / cancel / diagnose`、`decision.create / answer`，以及合入立即重试、附说明转交 Agent 和完成结果登记。命令返回实际结果、当前等待原因和合法下一步；桌面调度器不在线时明确说明记录已保存、尚未派发。工作与工单诊断汇总当前阶段、推进方式、等待原因、实际活动轮次、执行会话、依赖、自动推进开关、资源占用、合入处理者、失败与重试次数、最近失败和下次重试，并返回合法操作及作用范围。CLI 帮助可查询单个方法的参数、适用状态和示例。

### 暂离（尚未实现）

暂离用于睡觉等用户离开期间，由一个 agent 低频巡视所有未结束的工单，发现执行卡住或无人推进的情况并汇报到 Inbox，不代替用户处置。巡视间隔支持半小时、一小时。
