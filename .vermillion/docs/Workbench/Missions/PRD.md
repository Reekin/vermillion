# 工作与工单

WorkItem 是可独立执行和验收的单位，由开工分支创建（见 [工作台 · 开工](../Think/PRD.md)），或由用户在 工作台 → 工作 页手动创建（引用手改的文档或 Issue，冷启动一个 Worker）。领域 Owner 也可以按[自动修复授权](../Domains/PRD.md#自动修复授权)为 Issue 创建修复工单，这类工单关联来源 Issue、巡检会话和授权判断，走同样的调度、审阅和验收流程。

允许路径限定代码修改范围；是否使用 worktree 由 Worker 根据项目和本次工作判断，需要时自行创建并登记目录与分支，否则在 workspace 根执行。

工单主体是对文档的引用（路径、段落、commit），不另存需求副本。自身保存标题、范围与允许路径、验收条目、所需资源、依赖的工单、来源设计会话与执行会话、运行记录、证据、review 处置和决策。验收条目只描述做完后能观察到什么，不规定验收方法；每条一到两个短句，先说从哪进、再说看到什么。证据摘要面向用户，只说改动后能看到的行为变化；commit、分支、测试命令、review 和验收过程记在证据的命令与附件里，不写进摘要。

风险等级：R0 只读、R1 可丢弃制品、R2 项目内可回滚。影响共享环境的操作（发布、部署、推送远端等）不建工单，由用户在工作台会话页和设计伙伴一起完成。

## 引用定位

工单引用由文件路径、固定 commit、可选段落定位与独立的说明组成。段落定位使用文档实际标题；同名标题用完整祖先标题路径区分。定位不包含自由描述或行号，说明不参与变化判断；省略段落定位表示引用全文。

创建工单或更新 refs 时，工作台在指定 commit 上校验文件与段落可以唯一定位，无法定位时指出具体引用并拒绝该次写入。已保存引用无法定位时明确报告，不静默按全文处理。标题被删除或更名属于原引用范围的变化，须报告定位失效并由合同更新确认新位置，不自动猜测替代标题。

文档合入按每条引用的实际范围判断：范围外变化不升级合同、不发送文档变更通知、不更新该条引用 commit；范围内变化只更新对应引用并发送相关差异。同文件中未变化的其他引用保留原 commit。通知与合同更新遵循[执行循环规范](Standards.md#执行消息)。

## 工作

工作覆盖一次开工从准备到交付的全过程。work.start 接收成功就产生一份可查询、可管理的工作，名称取开工范围或来源会话标题，准备期间可以完善。准备阶段不预先创建空工单。一份工作包含一次准备和它产生的若干张工单；准备完成后仍保留工作入口、来源、准备结果和关联工单。手动创建和领域自动创建的工单单独管理，不补造准备阶段。

工单的业务阶段和会话是否在运行分开显示。主流程为准备、排队、执行、待合入、已关闭，取消是另一种结束结果；暂停、待用户决定和阻塞原因附在当前阶段上，不存在人工接管模式。处于执行阶段不代表 Agent 此刻正在运行，界面同时显示这一轮是在运行、已停止还是状态未确认。一轮确实停止后才释放它占用的并发名额。

准备完成时，准备分支通过 CLI 登记本次全部工单、文档依据和目录，工作台核对后等准备轮结束再开始执行工单。准备轮正常结束或已经建了一张工单，都不算准备完成。准备被暂停或取消时，已建的工单也不会开始执行。准备完成后，各张工单按各自依赖独立推进。

工作详情展示准备及工单的当前情况；全部工单结束后显示完成或含取消的结束结果，不把部分取消显示为全部交付。工作层提供暂停全部、恢复全部推进和取消剩余工作，只作用于未结束部分；单张工单操作只作用于本单，已完成成果与记录保留。准备中的操作目标为准备过程，进入工单执行分支后的目标为该工单。

## 看板

工作看板在 工作台 → 工作，展示当前 workspace 的全部工作及独立工单。顶部工具条提供自动推进开关、执行并发上限与执行中、等待中、已结束统计；统计按准备过程和独立执行工单计数，工作分组不重复计数。

看板按来源会话树分组，组标题使用会话列表中的树标题。同一会话树的多次开工、所属工单和来自这棵树的独立工单放在同一组；没有来源会话树的归入「独立工单」。分组可展开收起，切页后保留展开状态；从工单链接进入时展开所属分组并定位目标。

组内每次开工保留一个可展开的工作条目，建单前显示准备情况，建单后在其下展示关联工单。同一来源的多次开工仍可分别查看和管理，每张工单只出现一次。工作名称使用开工范围，未填写时使用来源会话标题；长范围在列表中截断，完整内容可查看。工作条目只展示名称、工单数量、最近变动时间、当前状态与适用操作，不重复列出下方工单的标题或状态。准备记录与已取消记录保留可见。

信息层级为会话树、工作、工单：树标题负责分组，工作与工单用适度缩进区分，不叠多层卡片。标题是主要信息，时间、数量和运行信息是辅助信息；次行只放具体等待原因或必要说明，不重复状态。间距与对齐参考[交互示意页](mock/workspaces.html)和[窄窗口](mock/narrow.png)效果；分组、内容与操作以本文为准。

每张工单一行，布局一致：风险标签、标题、运行信息（turn 数和最近变动时间，始终显示）、状态、适用的暂停或恢复入口，以及固定位置的取消 × 和「会话」。关联工单与独立工单的信息和操作一致。× 只在 hover 这一行时出现，但始终占位；状态、时间与操作在各行对齐，没有会话时会话位留空。长标题不挤压状态和操作，窄窗口下辅助信息可以换行。

工单处于等待时，状态使用具体阶段，例如「退回待续做」「合入受阻」「等待用户」，并在次行显示简短等待原因。「会话」跳到工单的执行会话：统一进入工作台 → 会话，fork 分支定位到对应节点，冷启动会话直接选中。工作层操作遵循[工作](#工作)，工单层操作只作用于本单；已结束的标题和状态适度降灰，仍保持可读。

排序规则是未结束在前、已结束在后，同类按最近变动时间从近到远，不再按具体状态细分。已关闭和已取消算已结束，其余都算未结束。一组里只要还有未结束的内容，整组就算未结束；同一组始终排在一起。组内的工作和工单、工作下的工单都按同样规则排序。

工单的变动时间是它最近一次更新的时间；工作取准备和关联工单中最新的时间；会话树分组取组内最新的时间。页面显示的时间就是排序依据，打开页面本身不改变顺序，时间相同时顺序稳定。状态更新后重新排序，展开状态保留。标题栏的 workspace 选择器切换看板范围。

## 工单面板

工单有一个统一的详情面板，以弹窗打开。弹窗标题使用工单标题，首屏固定回答当前在做什么、为什么等待、下一步由谁处理、用户是否需要操作；风险、状态、工单 id 和时间作为辅助信息。「会话」进入执行会话，「来源」回到来源设计会话的 fork 点，滚动长内容时仍能直接使用。

当前进展反映真实状态。等待时显示具体阶段、最近原因、当前处理者、恢复条件或下一步，以及已等待多久；不需要用户操作时明确说明。提交被退回后，显示退回原因、原 Worker 是否在运行、是否已收到续做要求，不笼统显示成「排队中」。失败信息先给可读摘要，展开后看原始原因和阻塞文件；没有记录的细节不做推测。

当前进展下方是按时间排列的关键事件，默认显示最近事件，可展开完整历史。事件使用用户可理解的动作描述，覆盖开始执行、合同调整、提交验收、合入检查、退回及通知送达、恢复执行、合入完成；run id、内部 stage 和 `done` 等内部字段只出现在技术详情里。

其余材料按「任务要求」「验收结果」「审阅意见」「检查与附件」分组折叠。折叠标题给出目标、通过数、处置数等摘要；验收要求与对应结果成对展示，不在面板不同位置重复全文。空的依赖、决策、附件等区块不占据页面；待用户答复的决策提升到当前进展区并提供操作。工单关闭后，当前进展改为成果摘要、合入 commit 和验收结论，历史退回与失败保留在事件记录中。

会话消息里出现的工单 id（开工分支的合同、设计伙伴的回复、决策卡里的相关工单）不以裸 id 显示，渲染成一枚工单标记：风险标签、标题、状态胶囊，状态随工单实时变化。点击标记进入工作台 → 工作并定位工单详情。

## 流转

工单依照[工作](#工作)中的阶段流转。Worker 通过 CLI 登记业务进展、提出决策和提交成果；程序完成派发、条件校验与合入。自然语言回复和单个轮次结束不代替业务交接，暂停或等待期间保留阶段、成果、固定执行会话与 worktree。

自动推进默认开启，执行并发上限默认为 2，每个 workspace 保存自己的设置。准备和 Worker 共用这个并发上限，普通会话聊天不受限制。一张工单要开始执行，需要 `dependsOn` 里的工单全部关闭，并且 `needs` 声明的资源没有被执行中的其他工单占用。`needs` 只写同一 workspace 内不能同时操作的具体对象；各自独立的浏览器、桌面和验收实例可以并行，不因为用了同类工具而互斥。`needs` 可以用 `workItem.update` 调整，调整后按新声明判断。前置工单被取消时，依赖它的工单停在当前阶段，显示等待用户处置依赖。

排到一张工单时，执行会话切换为 Worker 角色和 Worker 模型配置，然后收到合同开始执行。没有来源会话的独立工单冷启动一个 Worker，合同作为第一条消息。

Worker 在选定的工作目录完成开发、review 和冷验证。使用 worktree 时，提交前 rebase 到当前主分支；在 workspace 根执行时直接提交本次成果。工作台接收证据，默认自动合入，失败处置见[合入进度与处置](#合入进度与处置)；合入成功后立即关闭工单，Inbox 收到已合入通知，不等待 worktree 清理。纯操作工单及仅交付仓库外独立产物的工单通过验证后直接关闭，保留证据与产物位置，无需 Git 提交或合入。允许路径中的仓库外路径不参与 Git 成果检查；同时包含仓库内成果时，仓库内部分仍须完成提交检查与合入。用户在已合入通知上可以附理由回滚：工作台还原这次合并，原 Worker 带着理由续做。

worktree 由后台定期清理，默认每 5 分钟检查一次，工单刚结束时不立即删除。只清理已经没人使用的登记目录及其分支；排队、执行、待决策或续做还要用的目录都保留。在 workspace 根执行的工单没有要清理的目录。目录被占用或删除失败时等下次再试，删到一半的目录下次继续删完，再删除分支；不重开工单、不占 Worker 并发，也不产生决策卡。不是清理造成的、Git 已不再登记但仍有内容的目录保留待检查。重启后待清理的目录仍会被清理。清理操作提供 CLI。

需要改变尚未获准的需求、超出授权或存在必须由用户选择的取舍时，Worker 发决策卡并结束本轮，工单保留阶段并登记等待用户的事项；用户在决策卡或对应会话的决策回复模式中答复，交接规则见 [Inbox · 决策卡](../Inbox/PRD.md#决策卡)。能自行处理的技术问题继续处理，不因 review 或验证达到固定轮数而自动要求用户决定。分支与主分支代码冲突由 Worker 自己在 worktree rebase 解决后重交。

合同有修订号，只有 objective、scope、acceptance 和 refs 这些决定交付内容的字段变化时才升级；改 title、needs、dependsOn 不升级，也不会让执行中的提交被拒。提交时要注明依据的合同修订号，工作台只接受依据当前合同的提交。Worker 读到新合同、处理完影响后就可以在当前轮提交；依据过期时，已有成果和证据保留，只需更新依据和受影响的结果。

执行期间，其他会话或用户对合同的调整、引用文档的合入，会立即通知执行会话。执行会话自己做的调整和文档合入只记录，不回送给自己，也不打断当前轮；例如 Worker 自己加了 dependsOn，可以正常结束本轮，之后再按等待条件处理。合同调整、文档合入、提交退回和用户决定的通知各只送达一次；引用文档的 diff 只出现在通知和执行历史里，不写进合同。`workItem.cancel` 中断执行会话，已登记的 worktree 交给后台清理。

### 合入进度与处置

工单在待合入阶段区分等待合入、正在合入、合入受阻和原 Worker 处理中。列表与详情显示实际进度、最近失败原因、阻塞文件及当前处理者，不显示自动重试倒计时。

程序对已通过提交检查的成果执行一次正常合入。失败保留成果与检查点，提供立即重试、交给原 Worker 和取消入口；监工在周期检查时读取相同事实。主工作区改动归属等需要用户判断的阻塞进入 Inbox，不能擅自提交、stash 或丢弃用户修改。

交给原 Worker 时，把当前成果、失败原因和用户说明送进它的固定会话，并返回是否真的送达；只是排上队不算送达。原 Worker 处理本单的冲突、rebase 和受影响的验证，不重做未受影响的开发与验收；最终合入主分支仍由工作台执行。

合入、重试和回滚依次进行，同一次合入不会同时执行两遍。Worker 通过 CLI 登记处理结果，工作台核对实际 Git 结果后关闭工单。

### 执行、审阅与验证

执行与材料交接由 [Worker](../../../../packages/workbench/roles/worker.md)、[Reviewer](../../../../packages/workbench/roles/reviewer.md) 和 [Verifier](../../../../packages/workbench/roles/verifier.md) 指令规定。界面验收实例由工作台在独立桌面启动，不出现在用户操作屏幕上。

验证结果区分通过、发现缺陷、条件不足和未完成；条件不足与未完成不算产品缺陷，也不算通过。只有要求全部得到验证且符合文档终态时才能完成交付。有效的逐项观察和证据随续做保留，无关文档更新不使其失效；修复或需求变化只复核受影响部分。审阅与验证的交接、进度查询和续做由角色 prompt 规定。

### 执行控制

一张工单固定使用一个 Worker 会话。在设计讨论、Worker 会话和普通 fork 里聊天，都和普通会话完全一样：发送、追加、Stop、继续都照常可用。聊天不改变工单阶段，也不会按消息文字推断出业务动作。从历史节点 fork 只用于讨论，不能把工单的执行转过去。

自动推进开关控制 workspace 的新准备、Worker 程序派发、监工自动检查和后台自动巡检。关闭后不启动新自动动作，已开始的轮次、合入和结果登记可以收尾；重新开启不解除用户明确暂停或未解决的业务等待。

工作和单张工单保留明确的暂停、恢复与取消操作。暂停阻止目标的新程序派发和监工处置，并中断目标当前业务执行，保留成果；整份工作暂停还停止监工的新检查轮。取消结束目标并保留历史。单张工单暂停不阻止监工检查同一工作中的其他工单。恢复使未结束目标重新具备推进条件，仍检查依赖、资源和业务等待。

普通 Stop 只中断当前会话轮次，不隐式暂停整份工作、不改工单阶段。用户主动停止的事实可查询，不能被自动派发或监工当成故障自行续做；用户在原会话继续，或明确恢复该任务后，才继续推进。

业务 CLI 会检查调用者是不是这张工单的 Worker、工单是否被暂停或取消，以及依赖和资源是否满足。派发、继续和合入不会重复启动已经在运行的执行；动作不适用时返回当前情况。这些检查只针对业务 CLI，不限制普通聊天和 Agent 的其他工具调用。

### 运行失败与恢复

每次派发都有明确的起因：新任务、用户明确继续、决策答复、合入转交或新的业务通知，一个起因只派发一次。等依赖或资源时，这次派发排队等着；派发失败时保留原因和没送到的内容，等用户或监工处理。应用重启、刷新状态或看到失败记录，都不会自动把同一批内容再发一次。准备和 Worker 都按这个规则。

准备、Worker 与合入失败时，保留阶段、成果、最近的错误和可执行的下一步。一轮是否还在运行以引擎报告为准，不会因为一段时间没有新消息就判定失败；查看进度见[读取会话消息](../Roles/PRD.md#读取会话消息)。

Worker 轮次结束但没有提交或决策等交接时，工单保持未交付，显示会话已结束与缺少交接。程序不自动催办、不生成续跑提示、不安排多档失败重试。异常由监工在周期检查时判断，具体处置职责见角色指令。

准备未完成就中断时，保留已有文档、工单与会话，提供明确的重试入口；完整交接前不创建监工。

应用重启后，按工单和固定会话的实际轮次展示当前情况；暂停、取消和用户主动停止依然有效。重启不会重新派发正在执行的工作，也不会因为之前有轮次结束就自动续跑。

### 监工

准备完成登记、准备轮结束后，工作台从准备的最后一轮 fork 出监工会话并发起第一次检查，时机与开始执行工单相同。一份工作只有一个监工，之后的检查都复用这个会话；没有准备过程的独立工单没有监工。

仍有未结束工单且允许自动推进时，每轮检查结束后按[监工角色检查间隔](../Roles/PRD.md#检查间隔)发起下一轮。上一轮没结束就不发下一轮，也不累积检查次数。出现异常时立即记录和展示，但不额外触发检查。

若全部未结束工单都明确在等待用户（未答复决策、实时待审批或待输入、用户暂停或主动停止），程序不唤醒监工，保留原检查期限。用户答复或恢复、运行等待变化后重新判断：未到期继续等，已到期只检查一次，不补等待期间的次数。仍有其他工单推进，或有异常、缺少交接、受理结果或运行状态未确认时，继续正常检查；仅依赖或资源等待不作为跳过检查的依据。

自动推进关闭期间，检查时间照常计算；重新开启时如果还没到时间就继续等，已经过了只检查一次，不补关闭期间错过的次数。

整份工作暂停时不启动新的监工检查；恢复且自动推进已启用时检查一次，再恢复周期。全部关联工单关闭或取消后停止巡视，保留监工会话与记录。监工检查不占 Worker 程序派发的并发名额。

应用重启后继续使用原来的监工会话，不重新 fork：正在运行的检查等它结束再计时，空闲的按原来的检查时间继续。某一轮检查失败时记录原因，之后仍按同样的周期检查，不另设退避或再加一层监工。

工作详情可进入监工会话并查看最近检查、当前运行情况及下一次检查时间。程序向监工提供所属工作与工单的查询标识；监工的判断、动作与行为边界由[监工角色](../Roles/PRD.md#监工)定义。

### CLI

Worker 可通过 `asksource` 询问开单来源；会话消息读取和通用 `steer` 的行为见[会话读取与通信](../Roles/PRD.md#会话)。来源位置使用工单记录的设计会话与开单 turn。

工作与工单查询、准备完成登记、业务进展与依赖调整、提交成果、决策答复、暂停/恢复/取消、继续原 Worker、合入重试和结果登记都提供 CLI，与界面效果相同。操作返回实际结果和阻塞原因；派发或发送实际没有成功时，不能只记下请求就报告成功。

诊断分别展示业务阶段、固定会话及其真实运行状态、等待事项、依赖、自动推进开关、资源占用、成果和失败原因；工作诊断另外展示监工会话与检查情况。全局 CLI 帮助按对象与功能分组列出方法，明确区分 Issues 问题与建议记录、WorkItem 执行工单；单方法帮助列出适用状态、参数和示例，这两个列表方法说明各自的查询范围。
