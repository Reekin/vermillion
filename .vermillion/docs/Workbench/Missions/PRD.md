# 任务与工单

## 任务

Mission 是一项工作目标及其文档 revision 序列，状态为进行中、已完成、已取消。revision 是「这些文档在这个 commit 的内容」：从提交弹窗以「新任务」创建，或以「补充到现有任务」追加；勾选的文档里有本地改动的先提交，没有改动的直接引用当前 commit，所以已提交的文档也能开任务。「仅提交」只保存文档，不产生任务也不触发处理。

任务由管家判断目标是否达成并收尾：目标已达成标为已完成，目标放弃标为已取消。系统在完成任务时检查本任务下没有未结束的工单；工单全部结束本身不代表目标达成。之后补充 revision 会让任务回到进行中。

重复工单被取消、需求由其他任务的工单承接时，管家在原任务登记承接工单。承接工作尚未完成时原任务保持进行中；本任务工单全部结束及承接工单状态变化时，系统唤醒管家判断是否可以收尾。已处于这一状态的进行中任务也应得到收尾处理。管家确认承接工单已完成需求后，将原任务标为已完成，保存面向用户的结果说明和关联工单。任务卡片展示结果说明，关联工单可点击查看详情。

任务看板在 Workspaces → 任务，视觉打样见 [mock/workspaces.html](mock/workspaces.html)（截图 [mock/workspaces.png](mock/workspaces.png)，上半弹窗、下半页面）。顶部一行工具条：调度开关、并发上限步进器、一句等宽统计（进行中 / 待验收 / 已结束的数量），没有说明文字。

每个任务一张卡片。头部：状态标签、标题、右侧相对时间（页面模式下再加 revision 数与短 commit）、「管家会话」按钮、一个「···」菜单；「取消任务」只在这个菜单里，不直接摆在卡片上。正文：摘要（最多两行）、管家最近一句说明（一行）。下面每张工单一行：风险标签、标题、运行信息（等宽小字：角色、turn 数、最近时间；页面模式写全，弹窗模式只留 turn 数与时间）、状态胶囊、然后是固定的两个位：取消 × 和「会话」。× 只在这一行 hover 时显示，但始终占位，所以「会话」与状态列在所有行里对齐；没有会话的工单（排队中）会话位留空。运行记录不再单独成行，会话入口只出现一次。

独立工单不放在卡片里，用一个 eyebrow 小标题「独立工单」加一个带边框的列表直接列工单行。

以弹窗快速查看时只列进行中的任务和未关闭的独立工单，工具条右端一个链接「另有 N 项已结束」，点击即展开为页面；展开为页面后显示全部，已完成任务的工单标题和状态降灰。取消任务会先取消它下面所有未结束的工单。

任务看板和 Inbox 里的「会话」都跳到 Workspaces → 会话 并选中那个会话。

## 工单

WorkItem 是可独立执行和验收的单位，来自管家拆单，或由设计伙伴直接创建（独立工单，无 Mission：打包、测试等操作，以及不改设计的 bug 修复）。有允许路径的工单在独立分支和 worktree 里执行；没有的（纯操作）在 workspace 根执行。

工单主体是对文档的引用（路径、段落、commit），不另存需求副本。自身保存标题、范围与允许路径、验收条目、所需资源、依赖的工单、运行记录、证据、review 处置和决策。验收条目只描述做完后能观察到什么，不规定验收方法；每条一到两个短句，先说从哪进、再说看到什么。证据摘要面向用户，只说改动后能看到的行为变化；commit、分支、测试命令、review 和验收过程记在证据的命令与附件里，不写进摘要。[用户：这个验收单也是叽里呱啦看不懂]

风险等级：R0 只读、R1 可丢弃制品、R2 项目内可回滚。影响共享环境的操作（发布、部署、推送远端等）不建工单，由用户在思考页用现做模式和设计伙伴一起完成。

### 工单面板

工单有一个统一的详情面板，以弹窗打开：标题、状态胶囊、风险标签、目标、范围与允许路径、验收条目、引用的文档、依赖的工单、运行记录、证据、决策；底部一个「会话」按钮跳到 Workspaces → 会话并选中它的会话（排队中的没有会话则不显示）。任务看板里点击工单行的标题打开这个面板。

会话消息里出现的工单 id（管家、Worker、Supervisor 会话的合同和通知，设计伙伴建单后的回复，决策卡里的相关工单）不以裸 id 显示，渲染成一枚工单标记：风险标签、标题、状态胶囊，状态随工单实时变化。点击标记打开工单面板。[用户：类似于游戏里点击聊天栏里的道具]

## 流转

排队中 → 进行中 → 已关闭；已取消是另一个终态。需要用户决定时进入待决策，只挂起相关工单。用户答复先送达原 Worker，由 Worker 结合当前合同理解选项和备注。无需调整合同则直接继续执行；涉及目标、范围或验收变化时，Worker 先上报合同问题，由管家将决定落实为工单合同更新，更新前暂停开发与提交。判断答复复用原 Worker，不新增分类 agent、Inbox 选择或程序关键词判定。仅保存答复文字不解除合同阻塞。Worker 在同一会话里接着做（对话上下文和 worktree 都保留），答复的选项和备注作为下一条消息送达；只有原会话无法恢复时才新开会话并附上决策记录。

调度器按 workspace 并发上限和资源需求取单，默认并发 2；同一资源（如 browser）不能同时分配给多张工单；依赖的工单全部关闭后才取。Worker 在执行中发现自己依赖另一张尚未合入的工单时，把本单退回队列并登记这个依赖（原会话和 worktree 保留，取起时回原会话续做），而不是用决策卡请用户等待。Worker 发现合同与现实对不上（要改的文件不在允许路径内、验收条目在当前代码下无法成立等）时，把问题提交给负责该工单的管家：问题记入工单，本单退回队列（原会话和 worktree 保留），管家在自己的会话里收到工单 id 和问题，用工单更新、取消或决策卡处置；合同问题未解决时，本单暂停派发、不占 Worker 并发，不催促 Worker 继续，也不计为多轮未提交或运行失败；合同更新后 Worker 回原会话续做。Worker 与管家之间没有自由对话，管家的回应只能是这三种落到工单上的动作。决策卡只用于必须由用户做的业务取舍，不用于等待前置工单或申请范围调整。[用户：让一个任务上下游的 agent 相互 steer 不合适，只补 Worker→管家这一条，落文件、不自由回复] 待决策的工单不占并发。Worker 的一轮因运行时报错或被中断而异常结束时，工单退回队列，取起时仍回原会话续做（对话上下文和 worktree 都保留），中断原因作为下一条消息送达；连续多轮没有进展才换新会话从原 worktree 继续。这两种情况都计一次失败。失败后不立即重派，按失败次数等待 1、5、30、300 分钟后再取起（最多自动重试 4 次，让额度耗尽、网络故障这类外部原因有时间恢复）；第 5 次失败后不再自动重派，改为进入待决策：决策卡说明最近一次失败原因，选项是再试一次（计数清零，立即回原会话续做）或取消工单。[用户：允许重试4次，分别间隔1/5/30/300分钟][用户：只要是fail，都算外部原因吧？可以计attempts，也可以够次数后变决策卡，但没必要换worker]

Worker 提交前先把自己的分支 rebase 到当前主分支，再提交证据、review 处置和验收报告。验收通过即关闭：工作台合并分支并清理 worktree，Inbox 收到一张已合入通知。验收不通过，或合并遇到冲突（工作台以冲突文件列表为原因），都打回原 Worker 在同一会话里接着改（对话上下文和 worktree 都保留），打回原因作为下一条消息送达，只有原会话无法恢复时才新开会话并附上全部打回原因。用户在已合入通知上可以附理由回滚：工作台还原这次合并，工单带着理由打回原 Worker。

独立工单正常执行时不启动管家。首次出现 Worker 上报的合同问题，或用户答复需要修改合同时，按该工单启动管家会话；后续同一工单的合同处置复用该会话。管家读取原工单、阻塞原因和用户决定，处理原单合同并恢复原 Worker；此入口不重新执行需求拆单，只有确实需要改变拆分时才调整工单关系。独立工单保持无 Mission。

进行中改变方向时，管家通过工单更新调整目标、范围或验收并说明原因，Worker 立即收到；在调整送达那一轮里发出的提交视为依据旧合同而作废。待决策的工单被调整时，调整说明追加到其未答复决策卡的上下文里，用户答复时能看到合同变了；答复后连同调整一起送达 Worker。取消工单则中断执行；被取消工单的依赖方交由管家判断处置。审阅者不能自行新增验收要求。
