# 准备开工！

讨论结束，接下来请为开工做好准备工作——基于当前的讨论整理文档并建立工单，完成后结束 turn。本轮不实施代码，不再次调用 work.start。

1. 结合相关代码现状，把讨论结论更新到 `.vermillion/docs/`；通过 `vermillion docs.commit` 只提交相关文档，其余改动保留。已提交的文档直接引用对应 commit；不改设计的操作或修复不改文档。
  - 确保文档中体现的只是对最新设计的描述，不需要提及变化
  - 不需要提及具体的实现方案，只描述它的行为
  - 如果文档中有与讨论不一致的地方，调整好
  - 文档只留重要信息，不需要把细枝末节的业界通用做法都写进去（所以某些小改动是可以不改文档的）
  - 就地修改文档；不要创建替代版本或带版本号的副本
  - 只写 `.vermillion/docs/`，项目代码只读。工单、决策、运行与调度记录是工作台数据，任何模式都通过 CLI/RPC 操作，不直接编辑文件。
    - 当用户要求时，可以改写全局或项目中`.vermillion/roles/`下的内容
  - 文档中不写验收标准、不写验收方法——这些是体现在工单中的的。文档的职责是确保终态描述没有歧义。
  - 用户明确提出的边界性要求（"不要 X""只要 Y"这类容易被理解走样的话），在整理后的句子末尾附 `[用户：原话]` 作为出处，原话不超过两行。泛泛的目标不加。用户后来改了主意时，引文随句子一起改，旧引文删掉。引文只是依据，正文仍是整理后的正式陈述。
  - 如果用户向你反馈问题，你在查完问题后应当思考是什么导致的问题，以及设计上是否需要作出什么调整以规避此类问题，向用户提供方案，而不是仅回答问题。

2. 读取全部 `.vermillion/docs/domains/*.md`，判断本次改动涉及哪些领域，把相应 standards 加入工单 refs。refs 指明文档路径、段落和 commit；acceptance 根据文档与代码现状描述可验证结果。
3. 按范围调用 `vermillion workItem.create` 建单，传入消息中的 workspaceId 和 requestId。risk 按只读 R0（查日志、读代码、输出分析，不改变被操作对象）、可丢弃制品 R1（打包、生成草稿、跑测试；做坏了丢掉产物即可，项目本身没变）、项目文件修改 R2 填写（修改 Git 管理的代码或文档，能通过 revert 恢复；大多数功能开发属于这级）；修改代码时明确 scope.allowedPaths。多单的先后关系用 dependsOn，needs 只描述具体共享资源。
4. 对于非常简单的改动可以选择直接在main完成（并且完成后要立即提交），否则都需要自行创建一份临时分支和worktree，在 create 或 update 中同时登记 worktreePath 和 branch。不使用时在 workspace 根执行，并为共享目录写入声明同一具体资源。
5. 第一张工单另传当前 sessionId，将本分支登记为执行者；其余工单省略 sessionId，由调度器从准备轮末端 fork 执行分支。回复已建工单后结束本轮。会话 cwd 保持 workspace 根目录；排到执行时才切换为 Worker 并收到工单合同。

如果上次准备未完成，先核对本 requestId 下的工单、文档提交和 worktree，继续未完成的部分，避免重复创建。
