# Preparation!

Discussion is complete. Now prepare for Start work: organize Docs based on the current discussion and create Work items, then end the turn. Do not implement code this round or call work.start again.

1. Follow the Design Partner’s established document ownership and writing rules. Combine this discussion with the current code state and record it in Docs. Business code is read-only; Docs should contain design intent only, not instructions for specific implementation. Operations and fixes that do not change the design do not require Docs changes. Use `vermillion docs.commit` (with the current sessionId) to commit only relevant design Docs; leave other changes untouched. Cite already committed requirements by their original commit. If this includes role changes, update the global version first and then sync the source. Commit role source changes separately with Git; do not pass them to docs.commit or include role identity in refs.
2. Read the Domain definition and its standards. Based on this Work item’s development and acceptance needs, include all requirements and applicable standards in refs, specifying paths, sections, and commits. Use the Domain to discover standards, not as a substitute for reading their contents. Write acceptance criteria as observable outcomes; record specific actions and evidence during execution. Before handoff, confirm these materials are sufficient to explain the Work item’s goal, boundaries, and constraints.
- Decide the implementation approach and overall direction for Worker, and write it in the Work item so Worker can focus mainly on execution.
- Write the Work item in the same language as the design Docs.
3. Create a Work item using `vermillion workItem.create` for the scope, passing the workspaceId and requestId from the message. Set risk as follows: read-only R0 (inspect logs or code and produce analysis without changing the target), disposable artifacts R1 (package, generate a draft, or run tests; if something goes wrong, only the output needs to be discarded and the project itself remains unchanged), and project file changes R2 (modify Git-managed code or Docs that can be restored with revert; most feature development falls here). When changing code, specify `scope.allowedPaths` explicitly. Express ordering across multiple Work items with dependsOn; use needs only for specific shared resources.
  - Do not ask Worker to modify Docs in a Work item; the Design Partner must handle document changes. Worker may have permission to adjust Docs temporarily in a Work item, but the Design Partner should not directly assign document changes to Worker.
  - Before writing the Work item, check whether the work is coupled to existing in-progress Work items. Decide whether to add content to an existing item or create dependencies for the new item.
4. For a very simple change, you may work directly on main (and commit immediately when done). Otherwise, create a temporary branch and worktree, and register both worktreePath and branch in create or update. When no worktree is used, work from the workspace root and declare the specific shared resource for the shared directory.
5. Pass the current sessionId to the first Work item as well, registering this branch as its executor. Omit sessionId for the remaining Work items; the scheduler will fork execution branches from the end of the preparation round. After replying with the created Work items, end this round. Keep the session cwd at the workspace root; the session switches to Worker and receives the Work item contract only when scheduled for execution.

After creating all Work items and completing all directory registrations, use the Workbench’s preparation-completion entry point to register the complete Work item list and document basis for this requestId. Confirm the handoff succeeded before ending the turn; partial Work item creation or a text reply does not count as completing the registration. Use the current round’s CLI help and the Workbench-provided invocation information to identify the preparation-completion entry point.

If the previous preparation was incomplete, first check the Work items, document commits, and worktrees under this requestId, then continue what remains without creating duplicates.
